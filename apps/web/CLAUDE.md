# CLAUDE.md — `apps/web` (frontend)

Guidance for the **Next.js web app** (`@piluvitu/web`). O Claude Code carrega este arquivo **junto** com o `CLAUDE.md` da raiz — aqui ficam só os detalhes do frontend; orquestração/monorepo/CI estão na raiz.

Padrões: skill `padroes-produto-pilutech`.

## Tech Stack

- **Next.js 16** (App Router), **React 19**, **TypeScript** strict mode
- **Tailwind CSS 4** + **shadcn/ui** (New York style, CSS variables, slate base)
- **Keystatic 0.5 (reader-only)** — lê o conteúdo YAML em `content/` no build/ISR via `@keystatic/core/reader` (`lib/keystatic-reader.ts` → `lib/site-content.ts`). O **editor** `/keystatic` foi removido no slice ⑤; a edição agora é no `/admin` unificado.
- **TanStack Query 5** — data fetching (dev.to API)
- **Font Awesome 7** (`free-brands-svg-icons`, `free-solid-svg-icons`)
- **Storybook 10** — component documentation and manual UI verification
- **Vercel** — hosting do frontend com ISR

## Commands (web)

Os comandos canônicos (`make dev-web`, `pnpm --filter @piluvitu/web …`) estão na raiz. Específico do web:

- **Type checking without full build:** `pnpm exec tsc --noEmit` (de `apps/web/`)
- **E2E de SEO (build de produção):** `pnpm --filter @piluvitu/web test:e2e:seo` (ver _SEO_)
- **Recommended order before commit/PR:** `pnpm prettier:fix` → `pnpm lint` → `make test` → `pnpm --filter @piluvitu/web build`

**⚠️ Gotcha — Vercel é mais estrita que o build local com `implicit-any` em callbacks de libs de terceiro.** O `tsc`/`next build` LOCAL pode passar, mas o **install fresco da Vercel** (`--frozen-lockfile`) resolve o tipo do param como `any` quando ele vem de um `.d.ts` de terceiro — e aí `next build` quebra com `Parameter 'x' implicitly has an 'any' type` (já mordeu 2×: `onCreateEditor` do `@uiw/react-codemirror`/`@codemirror/*`, e a camera story). **Regra:** sempre **anote explicitamente** o param desses callbacks (ex.: `onCreateEditor={(view: EditorView) => …}`), não confie na inferência. Build local verde NÃO garante o da Vercel nesse caso.

### Content structure (Keystatic YAML)

**Singletons:**

- `content/site/profile/` — display name, avatar, role, bio, company
- `content/site/visit-card/` — up to 8 cells for the 3D card (triple-click avatar)

**Collections:**

- `content/socials/*/` — social links with order, icon mode, FA icon or image
- `content/carreiras/*/` — career history entries
- `content/pilulabs/*/` — catálogo PiluLabs (`pilulabs`): projetos e produtos PiluTech, com visibilidade, destaque e lojas (ver _PiluLabs_)

### Data flow

1. Server components call readers in `lib/site-content.ts` (`getSiteProfile()`, `getSocials()`, `getCarreiras()`, `getPiluLabs()`, `getVisitCard()`) — these read Keystatic YAML at build/request time.
2. `lib/blog-posts.ts` (`getBlogPosts()`, `getBlogPost()`) fetches MDX posts from the private `PiluVitu/piluvitu-blog` repo at build/ISR time via `@octokit/rest` using `BLOG_REPO_TOKEN`. Posts are cached 30 min (ISR tag `blog-posts`).
3. `lib/article-feed.ts` provides `ArticleCardView` — a unified type for both dev.to and blog posts. `devToToView()` and `blogPostToView()` convert each source. `mergeFeed()` merges and sorts by date.
4. `hooks/useArticleData.ts` fetches dev.to articles client-side via TanStack Query; merged with server-fetched blog posts in `ArticleSection`.
5. The visit card (`getVisitCard()`) feeds only the OG image (`lib/og-visit-card-image.tsx`); the home no longer shows it (2026-11 redesign).

### Font Awesome no conteúdo

Os ícones disponíveis vivem em `lib/visit-card-fontawesome.ts` (`VISIT_CARD_FA_ICON_MAP`, `VISIT_CARD_FA_SELECT_OPTIONS`). O `keystatic.config.ts` usa `fields.select({ options: VISIT_CARD_FA_SELECT_OPTIONS })` no campo `fontawesomeIcon` (o reader valida contra as opções). A **edição** do ícone é no `/admin/socials` (DS V2, com seu próprio picker `fa-icon-select`). Para adicionar um ícone novo: importe-o no map e adicione uma entrada nas select options. ### Remote images

Permitted image hosts are configured in `next.config.mjs` (`images.remotePatterns`). Adding a new external image host requires updating that list.

### Theme

O tema é o **Design System V2 "Cloud (cyan)"** — dark-first, acento ciano. **Os tokens (cores, radius, fontes, keyframes) vivem em `packages/ui/src/styles.css`** (`@piluvitu/ui`, compartilhado com `apps/financas/web`), não mais em `app/globals.css`. `app/globals.css` importa esse pacote no topo:

```css
@import 'tailwindcss';
@import '@piluvitu/ui/styles.css';
@source '../../../packages/ui/src';
@plugin '@tailwindcss/typography';
```

O `@source` é obrigatório — sem ele o Tailwind v4 compila normalmente (não quebra o build) mas **descarta silenciosamente** toda classe exclusiva de `packages/ui`. `scripts/check-tailwind-source.mjs` (raiz do monorepo) é o gate contra essa regressão: roda depois do `next build` nos scripts `build` **e** `build:ci` do `apps/web/package.json` (o `ci.yml` roda o `build:ci`, então PR e Vercel pegam a regressão) e falha se a classe sentinela definida em `packages/ui/src/styles.css` sumir do CSS emitido em `.next`. O nome exato dela está em `SENTINEL_SELECTOR`, no topo do script.

⚠️ **NUNCA escreva o nome da classe sentinela por extenso em nenhum arquivo dentro de `apps/web/` — nem em documentação.** A detecção automática de conteúdo do Tailwind v4 varre **todo** arquivo não-ignorado da árvore do app, independente de `@source`, e `.md` entra nessa varredura. Um literal solto aqui faz o Tailwind gerar a sentinela sozinho, e aí o gate passa **mesmo com o `@source` quebrado** — desativando exatamente a proteção que ele existe para dar. Isso já aconteceu uma vez, nesta seção, e foi pego na revisão da Task 2 do plano do design system. Referencie o `SENTINEL_SELECTOR` do script, nunca o literal.

⚠️ **`apps/web` avisa até em `dev` — diferente de `apps/financas/web`.** MEDIDO na Task 11: comentando o `@source` acima e subindo `pnpm --filter @piluvitu/web dev` (webpack, porta 3333), a sentinela já sai ausente do CSS servido em `/_next/static/css/app/layout.css` (sem precisar de build nenhum) — o webpack do Next não empresta ao dev server o "atalho" que o plugin Vite empresta ao seu (que escaneia o grafo de módulos e mostra as classes certas mesmo com `@source` quebrado, só falhando de verdade no `vite build`). Detalhe completo, incluindo a evidência dos dois lados, em `packages/ui/CLAUDE.md` § _Gate do design system: `@source`, o sentinela, e a assimetria dev/prod_.

Depois do `@import`/`@source`, `app/globals.css` guarda só o que é **específico deste app**: `@utility container`, a camada de compat de `border-color` do Tailwind v4, a aplicação de `border-border`/`bg-background`/`font-sans` em `@layer base`, o dual-theme do shiki (`code[data-theme...]`) e as regras `.post-prose` do blog. `:root`/`.dark` (as custom properties que os tokens referenciam) ficam só em `packages/ui/src/styles.css` — mapeados sobre os tokens shadcn existentes: a cor de marca do V2 (ciano `#38bdf8`) entra como `--primary` (atenção: no shadcn `--accent` é o hover bg, não a marca). **Dark é o padrão** via `next-themes` (`defaultTheme="dark"` em `app/(site)/layout.tsx`); o `mode-toggle` alterna pro light.

`cn()` também pode vir de `@piluvitu/ui/cn`. Os 14 componentes shadcn (`aspect-ratio`, `avatar`, `badge`, `button`, `card`, `command`, `dialog`, `dropdown-menu`, `form`, `input`, `label`, `separator`, `skeleton`, `textarea`) foram migrados pra `packages/ui/src` e são importados como `@piluvitu/ui/<nome>` (ex.: `import { Button } from '@piluvitu/ui/button'`) — **sem barrel**, um export por componente em `packages/ui/package.json`. Só `components/ui/sonner.tsx` continua em `apps/web` (acoplado a `next-themes`, que o pacote compartilhado não pode carregar). **Medido:** nem o CSS (`@import`/`@source`) nem o import direto de `.tsx` (incl. `'use client'`) do pacote workspace precisam de `transpilePackages: ['@piluvitu/ui']` em `next.config.mjs` — build real do Next/Turbopack consome os componentes sem essa flag. Ver `packages/ui/CLAUDE.md` para a estrutura completa do pacote.

⚠️ **M3 (fix final, branch design system do financas — registrado, sem código aqui):** `packages/ui/src/button.tsx` ganhou `cursor-pointer` na string base do `buttonVariants` (fix round 1, achado da Task 9 da SPA de finanças — ver `packages/ui/CLAUDE.md`). Como `Button` é **compartilhado**, esse é o único rendered-CSS change que este app herda do branch de design system do financas além do que já era esperado — kept deliberadamente (era uma lacuna real, não uma escolha visual nova): antes, todo `<button>` daqui usava o cursor default do navegador em vez da mãozinha de clique, sem que nenhuma tela local dependesse de um `button` cru pra notar. `apps/web` (jest + tsc) reexecutado depois da mudança — verde, nenhum teste dependia do cursor.

- **Fontes:** Plus Jakarta Sans (corpo/títulos, `--font-sans`) + JetBrains Mono (labels/datas/tags, `--font-mono`), via `next/font` no `app/layout.tsx`. O fallback fica aninhado no `var()` (`var(--font-plus-jakarta, ui-sans-serif, …)`) pra sobreviver onde o RootLayout não roda (ex.: Storybook).

### Votaí (`votai.piluvitu.com.br`): host, proxy, links, SEO e medição

A votação de filmes virou o **Votaí** (nome com acento na interface; sem acento no DNS) em **`https://votai.piluvitu.com.br`**, servido pelo **mesmo projeto da Vercel** (`pilu-vitu-dev`). Precisa ser `*.piluvitu.com.br`: a sessão é o cookie do `ramielle.piluvitu.com.br`, same-site com o Votaí (o `SameSite=Lax` atravessa o `fetch` com `credentials: 'include'`); em outro domínio ele vira cookie de terceiro e o Safari bloqueia.

- **Origens fixas em código (`lib/votai.ts`), nunca do pedido:** produção `https://votai.piluvitu.com.br` e `https://piluvitu.com.br`; dev/E2E `http://votai.localhost:3333` e `http://localhost:3333` (o Chromium resolve `*.localhost` para o loopback). O texto nasce com "Texto", com o foco no campo Texto do painel e tudo escolhido, para a pessoa escrever por cima.
  - **Imagem:** ligar a ferramenta sem imagem abre a escolha do arquivo (`accept` PNG e JPEG, que é só sugestão: quem decide são os bytes, em `prepararImagem`). A imagem pronta espera o clique, o arraste (cabe na caixa, com a proporção) ou o "Inserir no centro" (tamanho natural, pixel CSS em ponto, até 60% da página). Recusas em `role=alert` com o que fazer: não é PNG nem JPEG, não decodifica, falha do navegador e o teto de 50 MB, que soma as imagens que algum passo do histórico usa; a que nenhum passo usa sai da memória e tem a URL revogada.
  - **Objetos na tela** (`QuadroDeObjetos`, só quando a página aberta já foi desenhada, porque é o tamanho dela que posiciona): um `role=application` "Objetos da página N" por cima da folha, para NVDA e JAWS deixarem as setas com a página. Cada objeto é desenhado num SVG do tamanho da página, em pontos (o marca-texto com `mix-blend-mode: multiply` sobre o canvas, como o `BlendMode.Multiply` do PDF; o texto pela `linhasDeBase`, na família CSS equivalente; o traço pelo `caminhoDoTraco` do `@piluvitu/tools/pdf-traco`, o mesmo do Worker), e por cima vai um botão por objeto (`role=button`, `tabIndex=0`, `aria-roledescription` "objeto do PDF", o nome com tipo, conteúdo, posição e tamanho, `aria-describedby` para as instruções escritas embaixo da área), com 4 px de folga em volta para linha reta e traço fino darem para pegar. O escolhido tem anel na cor primária com contorno branco e a alça do canto de baixo à direita (a mesma do teclado), de 20 px e 44 px em `pointer: coarse` (`pointer-coarse:size-11`).
  - **Teclado no objeto:** setas movem 1 ponto e Shift+setas 10; Alt+setas redimensionam 1 ponto (Alt+Shift+setas, 10) puxando o canto de baixo à direita, e no texto mudam a letra (de 4 a 300 pontos), com a caixa junto. As setas, com ou sem Alt, têm `preventDefault` (Alt+← e Alt+→ são voltar e avançar do navegador no Windows e no Linux); com Ctrl ou ⌘ ficam com o navegador. Delete e Backspace apagam (o foco vai ao objeto seguinte, ao anterior ou ao quadro); Enter, no texto, leva ao campo Texto, e Esc no campo volta ao objeto; Esc solta o objeto (o foco vai ao quadro, que tem `tabIndex=-1`) ou cancela o arraste em curso. A posição nova é anunciada 500 ms depois do último passo ("Em 240 por 381, 120 por 80 pontos.", e no texto também a letra), não a cada passo.
  - **Ponteiro e toque:** com Selecionar, arrastar o objeto move só ele (`touch-action: none` no objeto e na alça), num passo só do desfazer, e o clique fora dos objetos solta o escolhido; fora dos objetos a página rola. Com outra ferramenta, os objetos deixam o ponteiro passar (`pointer-events: none`, ainda focáveis pelo Tab), para desenhar e criar por cima. Só o Desenhar trava a rolagem (`touch-action: none` no quadro), com o aviso "Desenho ligado…" nas opções; com as outras, o dedo que arrasta rola a página (o navegador manda `pointercancel`, e nada é criado) e o toque curto põe o objeto. O ponteiro é capturado no quadro; um segundo dedo não atrapalha o primeiro, e o mouse que soltou fora da página não trava o próximo arraste. O traço usa os `getCoalescedEvents` e a pressão só da caneta.
  - **Texto do próprio PDF:** com Selecionar, o clique fora dos objetos pergunta ao `textoNoPonto` se há texto ali; havendo, a tela diz (e anuncia) que editar o texto que já existe não é confiável e que o caminho é cobrir e escrever por cima, com o botão "Usar Cobrir".
  - **Painel** (`PainelDoObjeto`, um `role=group` "Objeto escolhido" embaixo da área, ou a frase de que nenhum está escolhido): X, Y, largura e altura em campos numéricos com rótulo (o texto não tem largura e altura: muda pela letra e pelo conteúdo), sempre dentro da página (largura e altura param na borda, sem mover o objeto); no texto, o campo Texto, a fonte (Helvetica, Times, Courier), negrito, itálico e o tamanho da letra; a cor numa lista com nome (dez cores) e no seletor do navegador ("Escolher outra cor"); a espessura (0,5 a 50 pontos); e "Apagar objeto". O que a pessoa escolhe no painel vira o estilo do próximo objeto do mesmo grupo (texto, desenho, formas e marca-texto).
  - **WinAnsi:** caractere que as fontes padrão do PDF não escrevem (emoji, ✓, CJK) nem entra no campo Texto: a tela o tira na hora, com o cursor onde a pessoa escrevia, e mostra um `role=alert` com os caracteres e o que fazer.
  - **Desfazer e refazer:** botões e Ctrl/⌘+Z, Ctrl/⌘+Shift+Z (e Ctrl+Y), fora de campo de texto. O histórico é da cena inteira (limite de 100 passos, do `pdf-regras`), e passos seguidos do mesmo objeto pela mesma origem (setas, Alt+setas, o mesmo campo do painel) em menos de 1 s viram um passo só. Desfazer o que mudou em outra página leva até ela ("Desfeito na página 1."). O foco fica onde estava se o elemento continua na tela e habilitado; senão vai ao botão usado, ao do outro sentido ou à ferramenta ligada.
  - **Cobrir e apagar de verdade:** com algum retângulo de cobrir na página aberta, aparece "Cobrir nesta página", com o aviso de que o texto continua no arquivo e o botão "Apagar de verdade o que está embaixo". Ele abre a explicação (a página vira imagem, perde a seleção de texto, fica maior, os links, os campos e os marcadores que levam a ela saem, o formulário XFA sai do documento inteiro, e continuam, com todas as letras, o título, o autor e as outras informações do documento e os anexos) e o foco vai para "Apagar de verdade nesta página", descrito pela explicação; Cancelar volta. Confirmada, a página fica marcada na cena (entra no desfazer), com "Só cobrir, sem apagar" para voltar. Só vira imagem a página marcada que tem cobrir.
  - **Gerar:** "Gerar PDF editado" (desabilitado com o motivo enquanto não há objeto), com o resumo ("3 objetos em 2 páginas.") e as páginas que vão virar imagem. Desenha o fundo de cada página marcada (`DocumentoAberto.fundo`, com os cobrir dela), manda ao `motor.editar` os objetos de cada página, só as imagens que eles usam e os fundos, e oferece o download de `<nome>-editado.pdf` (`nomeDoPdfDerivado`), com o foco no link. Enquanto monta, o "Cancelar" tem o foco, a área de edição fica `inert` e a escolha de arquivo, desabilitada. Mudar a cena descarta o resultado. A falha de um objeto (`falhaAoSalvar`) vem num `role=alert` com "Mostrar o objeto", que abre a página dele e põe o foco nele.

    | objetos, sem apagar de verdade | 4,4 s, +1.248 MB | +1.297 MB                | 0,25 s, +583 MB | 49 MB       |

- **Assinar** (`/tools/pdf/assinar`, o mesmo `editar.tsx` com `modo="assinar"`; fase 4, ver "Fase 4" no plano):
  - **Abrir:** as regras e as mensagens do editar, com "que dá para assinar" nos dois tetos, e o pdf-lib lendo também o formulário na mesma leitura (`useAbrirPdf` com `formulario: true`). O formulário lido fica preso ao documento aberto: um PDF novo traz o dele, e o recusado não herda o do anterior. O anúncio do aberto ganha o resumo do formulário ("formulario.pdf · 2 páginas. Formulário com 9 campos em 2 páginas.").
  - **Aviso:** o `AvisoDeAssinaturaVisual` (assinatura visual não substitui a com certificado, ICP-Brasil e gov.br) fica logo depois do aviso de privacidade, sempre, com e sem arquivo, e também no painel da ferramenta Assinatura, nos dois modos.
  - **Largura e colunas:** a página do assinar usa o `ToolPageShell` com `larga` (`max-w-3xl`, e `max-w-6xl` a partir de `lg`). A partir de `lg`, a área de edição tem duas colunas (`data-testid="editar-pdf-colunas"`): a página à esquerda, presa no topo ao rolar (`lg:sticky`), e o painel do objeto e o formulário à direita (24rem). Antes, uma coluna. A ordem no DOM é barra, opções, página, painel do objeto, formulário e gerar. O editar continua com uma coluna e a largura de leitura.
  - **Barra:** Selecionar e mover, Assinatura e Texto (para a data e o nome). Sem Cobrir na barra, o clique num texto do PDF não pergunta ao `textoNoPonto` nem mostra a dica de cobrir e escrever por cima. No editar, a Assinatura é a quarta das onze ferramentas, e funciona igual.
  - **Assinatura:** ligar a ferramenta sem assinatura pronta abre o `CriarAssinatura` nas opções. "Usar esta assinatura" guarda a assinatura na tela: o PNG entra no `imagens`, como as imagens da fase 3, conta no teto de 50 MB e fica enquanto ela está pronta ou algum passo do histórico a usa; o nome digitado fica com a cor. Anuncia "Assinatura pronta. …" e leva o foco ao "Inserir no centro" (com a página ainda sem desenho, ele fica parado, e o foco vai para "Criar outra assinatura"). Com ela pronta, as opções mostram o aviso, "Assinatura pronta" com a descrição em texto, a prévia, "Inserir no centro" (com o aviso na descrição, porque o foco cai nele, depois do aviso) e "Criar outra assinatura" (o criar ganha "Cancelar", que volta à pronta com o foco no botão). Pôr segue a imagem: clique, arraste (cabe na caixa com a proporção) ou o centro, com 180 pontos de largura (`LARGURA_DA_ASSINATURA_NA_PAGINA`). O nome digitado vira um texto em Times itálico de 28 pontos. Depois, volta para Selecionar e mover com o foco no objeto, que se move e redimensiona como os da fase 3. A assinatura continua pronta para outras páginas e outros PDFs, até a tela sair; a que é trocada e que nenhum passo usa sai da memória. Nada vai para `localStorage`, `sessionStorage` ou IndexedDB.
  - **Formulário:** o `PainelDoFormulario`, no estado do `useFormularioDoPdf`. Focar um campo de outra página abre a página dele sem anúncio (o "Na página N." do campo já diz) e sem tirar o foco do campo; o destaque aparece quando a página fica pronta, e a área rola até ele (`rolagemParaMostrar`, com 24 px de margem, sem suavizar com reduzir movimento). Os controles ficam registrados por id do campo (e o radio também pela opção) num mapa, para o "Ir para" dos obrigatórios, "Mostrar o campo" e o clique no widget.
  - **Gerar:** "Gerar PDF assinado" habilita com objeto, campo mudado ou achatar, e o motivo do botão parado é o `TEXTOS.assinar.gerar.semMudancas`. - ⚠️ **Um YAML que o reader do Keystatic recusa derruba o build.**
  - **A armadilha:** o site lê pelo reader (`getPiluLabs`), mais estrito que o `normalizarItem`. `tipo` fora das opções, booleano em texto (`listado: "true"`), `order` que não é inteiro, texto em número e `data: ''` lançam erro. Como o `.all()` faz `Promise.all`, um item derruba a coleção inteira: home, `/pilulabs`, `/api/admin/stats` e o `next build`. O `apps/pilutech-site` lê o mesmo `content/pilulabs/botai/index.yaml` no build dele (só as 4 URLs de loja, pelo `yaml`, sem o reader). A data inexistente sem aspas (`2026-02-30`) ele não recusa: o js-yaml a rola para `2026-03-02`. A chave sem valor ele lê como ausente.
  - **No admin:** o `pilulabsSchema` é mais estrito ainda (`https:`, host da loja, data real, chave sem valor recusada), e o `GET /api/admin/content/pilulabs` valida dentro de um `Promise.all`: um item recusado vira 502 na lista inteira, e o reorder também falha.
  - **Por que `data` é `fields.date`:** o `yaml` do admin grava `data: 2026-10-01` sem aspas, e o `js-yaml` do reader lê isso como `Date`, que um `fields.text` recusaria.
  - **A defesa:**
    - o registry do admin tem `omitirSeVazio: ['data']`, e o `serializeEntry` apaga a chave vazia;
    - o `lib/pilulabs-conteudo.test.ts` reprova o YAML que o reader recusa (`camposInvalidosNoYaml`, que espelha o parse de cada campo do `keystatic.config.ts`) e o que o `pilulabsSchema` recusa. ### Preview (draft mode)

**Achado de 2026-11-12 (corrigido):** `GET /preview/start?to=…&branch=…` ligava o draft mode (`__prerender_bypass`) e gravava o cookie `ks-branch` para **qualquer visitante**, sem sessão. Com isso a home e `/posts/<rascunho>` mostravam os rascunhos do blog privado (lidos com o `BLOG_REPO_TOKEN` do servidor) e o reader do Keystatic lia o site do GitHub no ramo que o visitante quisesse. O `ks-branch` saía sem `HttpOnly`/`Secure`/`SameSite` e sem prazo, e o `POST /preview/end` redirecionava para qualquer `Referer`.

**Revisão do mesmo dia (corrigida):** o `piluvitu_admin_gh` é `SameSite=Lax` e vai junto numa navegação vinda de outro site, então um link de fora ligava o preview do admin num ramo escolhido por quem fez o link. Como o repo do site é público, isso incluía `refs/pull/N/head` de um PR de fork (e `pull/N/head`, que o git resolve como `refs/pull/N/head`) ou um SHA, com o conteúdo e os feeds desse ramo (o servidor buscava as URLs dos feeds de fora). E o `/preview/end` exigia admin: depois do `unlink` ou com o GitHub fora do ar o "Sair" da faixa dava 401, e o preview seguia no navegador por até 1 hora. Medido num build de produção com um GitHub falso.

- **`GET /preview/start`** (`app/preview/start/route.ts`), nesta ordem, sem nenhum `Set-Cookie` e sem ligar o draft mode em cada recusa: `exigirAdmin()` (**401**); `Sec-Fetch-Site` igual a `same-origin` ou `none` (`navegacaoDoProprioSite`: link do próprio site ou URL digitada; `cross-site`, `same-site` ou ausente dão **403**); `to` (`destinoDoPreview`: caminho do próprio site, começa com `/`, sem `//`, `/\`, barra invertida nem caractere de controle, e a URL resolvida tem de ficar na mesma origem; o tab vira `//` no parser de URL) e `branch` (`branchValido`: `^[A-Za-z0-9._/-]{1,100}$`, sem `..`, sem começar com `/` ou `-`, sem começar com `refs/` ou `pull/` e sem ser um SHA de 40 ou 64 hex), senão **400**; e o ramo tem de existir no repo do site (`lib/admin/ramo-do-site.ts`, `ramoDoSiteExiste`: `GET /repos/{KEYSTATIC_GITHUB_REPO}/branches/{ramo}` com o token da pessoa, 5 s, e o `name` da resposta igual ao pedido; 404, erro, prazo ou ramo renomeado dão **400**). Admin: liga o draft mode, grava o selado, apaga o `ks-branch` e dá **307** para o `to` no mesmo host, com `Cache-Control: private, no-store`.
- **Cookie selado `piluvitu_preview`** (`lib/preview.ts`): `{ branch, login, exp }` cifrado com AES-256-GCM pela mesma chave do `ADMIN_TOKEN_SECRET` (`selar`/`abrir` de `lib/admin/token-cookie.ts`, com o nome do cookie como AAD: o `piluvitu_admin_gh` não abre como preview e vice-versa; o formato do `piluvitu_admin_gh` não mudou, `token-cookie.test.ts` decifra um à mão). `HttpOnly`, `Secure` em produção, `SameSite=Lax`, `Path=/`, `Max-Age` de 1 hora (`PRAZO_DO_PREVIEW = 3600`); o `exp` dentro dele é o que manda (vencido ou além de 1 hora, não abre).
- **`__prerender_bypass`:** o `draftMode().enable()` do Next 16.4.1 grava `HttpOnly`, `SameSite=None` e `Secure` fora do dev, **sem prazo** (`node_modules/next/dist/server/async-storage/draft-mode-provider.js`, idêntico na 16.4.5, conferido em 2026-11-16 com `cmp` entre as duas cópias instaladas). Num route handler o `cookies()` e o draft mode escrevem no mesmo `mutableCookies`, então o start relê o valor e o regrava com as opções do selado (Lax, 1 hora). Medido no `next dev` (com o `exigirAdmin` trocado só para a medição e revertido): a resposta sai com um único `Set-Cookie` do `__prerender_bypass`, com `Max-Age=3600; HttpOnly; SameSite=lax`; o selado vem igual e o `ks-branch` sai expirado. O draft mode do Next continua funcionando: só o envio entre sites (iframe de outro domínio) deixa de levar o cookie, e aqui o preview é navegação no próprio site.
- **`previewAtivo()`** (`lib/preview.ts`, server-only) devolve `{ branch }` só com o draft mode ligado **e** o selado abrindo, no prazo e com ramo válido. Lê o draft mode antes dos cookies: numa página estática ele é falso e o `cookies()` nem roda (a home e as páginas `○` seguem estáticas). **Todo leitor usa ele, nunca o `draftMode().isEnabled` nem o `ks-branch`:** `lib/blog-posts.ts` (rascunhos e `noStore`), `lib/site-content.ts` (`noStore`), `lib/keystatic-reader.ts` (`createGitHubReader` com `ref` = ramo selado) e `app/(site)/layout.tsx` (faixa "Pré-visualização do ramo …" e a medição). Um `__prerender_bypass` sozinho não mostra nada além do publicado.
- **`POST /preview/end`** (`app/preview/end/route.ts`): mantém as checagens de `Origin` (400) e `Referer` (400) e, **sem exigir admin**, desliga o draft mode e apaga o selado e o `ks-branch` (`desligarPreview()` de `lib/preview.ts`, o mesmo que o `POST /api/admin/github/unlink` chama), dando **303** para o `Referer` só se for da mesma origem; outro host ou `Referer` inválido vão para `/`. Desligar só apaga os cookies de quem pede, então exigir admin ali não protege nada e prende o preview no navegador.
- **Quem usa:** o `previewUrl` do `keystatic.config.ts` (`/preview/start?branch={branch}&to=/`) sobrou do editor do Keystatic, removido no slice ⑤; nada no app gera esse link hoje. Para usar o preview à mão, conecte o GitHub no `/admin` com a conta que escreve no repo do blog e **digite** a URL na barra do navegador (ou siga um link do próprio site). Sem o GitHub conectado, 401; vindo de link de outro site, 403.
- **Testes:** Jest com um `next/headers` falso (`lib/next-headers-falso.ts`: cookies do pedido, `Set-Cookie` da resposta e o draft mode como o Next grava) em `app/preview/start/route.test.ts`, `app/preview/end/route.test.ts`, `app/api/admin/github/unlink/route.test.ts`, `lib/preview.test.ts`, `lib/admin/ramo-do-site.test.ts`, `lib/blog-posts.test.ts`, `lib/keystatic-reader.test.ts` e `app/(site)/layout.test.tsx`; o GitHub é o `fetch` espionado (o `keystatic.config` é mockado, porque o `@keystatic/core` é ESM). E2E `app/preview/preview.e2e.ts` contra o build de produção: `GET` anônimo e com `piluvitu_admin_gh` forjado no `/preview/start` dão 401 sem `Set-Cookie`; `POST` sem admin no `/preview/end` dá 303 e expira os três cookies, e de outra origem dá 400 sem `Set-Cookie`; e o `__prerender_bypass` **verdadeiro** do build (`preview.previewModeId` de `.next/prerender-manifest.json`) com `ks-branch` e selado forjado não mostra a faixa. Um `__prerender_bypass` inventado nem liga o draft mode no `next start` (o Next compara com o id exato), então o teste confere antes que o draft mode ligou (`Cache-Control` com `no-store`; sem ele, a página estática sai com `s-maxage`); pula sem `E2E_BASE_URL` ou sem o manifesto. O caminho do admin fica só no Jest, porque o servidor perguntaria ao GitHub real. Para rodar contra um servidor já de pé numa porta livre (fora da 3333), o `playwright.config.ts` aceita `E2E_BASE_URL` e aí não sobe o `next dev`: `pnpm build && PORT=<porta> pnpm start` e `E2E_BASE_URL=http://localhost:<porta> pnpm exec playwright test preview.e2e`.

## Política de privacidade (`/privacidade`)

`app/(site)/privacidade/page.tsx`, com o texto em `lib/politica-de-privacidade.ts` (`POLITICA_DE_PRIVACIDADE`: título, vigência, resumo e seções com parágrafos de trechos, que são texto, link, e-mail ou código). A página renderiza esse texto e o `llms-full.txt` o serializa (ver _SEO_). Em vigor desde 2026-11-16, quando ganhou a seção "A Cloudflare na frente do site" (decisão do dono: o Cloudflare Web Analytics fica ligado). A versão de 2026-10-26 trouxe o Votaí: o domínio `votai.piluvitu.com.br`, o histórico público só com contagens e número de participantes, e o cookie descrito como do `ramielle.piluvitu.com.br`. O link fica no `HomeFooter`, sempre visível, depois dos links públicos e antes dos de login.

- **O que ela descreve:**
  - a medição da Vercel (seção acima);
  - os registros da hospedagem;
  - a Cloudflare na frente do site e do Votaí:
    - o proxy;
    - o Cloudflare Web Analytics, que a borda injeta em todas as páginas, inclusive `/admin` e o Votaí, sem cookie;
    - o teste invisível contra robôs (`/cdn-cgi/challenge-platform`), que grava o `cf_clearance`. Medido: é o único cookie que apareceu, gravado pelo POST do `jsd/oneshot`, e as páginas não devolvem `Set-Cookie`. ⚠️ A validade de 1 ano que a política cita é valor **medido em 2026-11-16**, não está em nenhuma página da Cloudflare (a de JavaScript detections fala em 15 minutos de vida da detecção, não do cookie). Pode mudar sem aviso: confira de novo sempre que a política for revista. A documentação também cita o `__cf_bm`, de 30 minutos sem uso;
    - o e-mail escondido dos robôs, o pré-carregamento (Speed Brain) e o Network Error Logging (só falhas; do IP a Cloudflare tira o ASN, o país e a área metropolitana e não guarda o IP).

    As fontes oficiais e a medição estão no comentário do teste dessa seção;

  - a votação, o Votaí (o que o `apps/ramielle` guarda no D1, o cookie do Better Auth, o backup e o histórico público: o que aparece sem login e que nunca aparece quem votou nem em quê);

- **A duração do cookie da votação é o padrão do Better Auth** (7 dias, renovados a cada dia de uso), porque `apps/ramielle/src/lib/auth.ts` não define `session`. Conferido no 1.6.25 e de novo no 1.7.13 (`expiresIn` 604800, `updateAge` 86400).
