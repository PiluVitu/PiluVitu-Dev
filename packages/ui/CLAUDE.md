# CLAUDE.md — `packages/ui` (`@piluvitu/ui`)

Guidance for the **shared design system package**. O Claude Code carrega este arquivo **junto** com o `CLAUDE.md` da raiz. Consumido por `apps/web` (Task 3 do plano `docs/superpowers/plans/2026-07-26-financas-ui-design-system.md`) e, desde a Task 4, por `apps/financas/web` (SPA Vite) — ver `apps/financas/CLAUDE.md` § _SPA_ para os detalhes do lado Vite.

## Propósito

`@piluvitu/ui` centraliza o **design system** compartilhado: tokens (cores, radius, fontes, keyframes — `src/styles.css`), o helper `cn()`, os **14 componentes shadcn/ui** (New York style, sobre Radix primitives) que eram exclusivos de `apps/web/components/ui/`, e componentes **não-shadcn** construídos direto sobre Radix primitives quando o caso de uso pede (ver `ajuda.tsx` abaixo).

## Por que não tem build

Não existe `dist/`, não existe passo de compilação — `tsconfig.json` tem `"noEmit": true`, e `package.json` → `exports` mapeia cada subpath (`@piluvitu/ui/button`, `/card`, …) direto pro `.tsx`/`.ts` **cru** dentro de `src/`. Os dois consumidores (`apps/web` via webpack/Turbopack, `apps/financas/web` via Vite) importam esse código fonte e cada bundler faz a própria transpilação — **medido** nas Tasks 2/3/4: nem CSS (`@import`/`@source`) nem os `.tsx` (incl. `'use client'`, JSX, `React.forwardRef`) precisam de `transpilePackages: ['@piluvitu/ui']` no `next.config.mjs`, nem de configuração equivalente no `vite.config.ts` — os dois bundlers resolvem um pacote workspace pnpm sem build próprio sem problema.

Isso não é só "menos trabalho" — é **necessário** pro `@source` funcionar (ver seção _Gate do design system_ mais abaixo). O scanner de conteúdo do Tailwind v4 procura classes em **texto-fonte**, no diretório que o `@source` aponta (`packages/ui/src`). Se este pacote publicasse um `dist/` pré-compilado/minificado em vez do `.tsx` cru, os dois apps consumidores precisariam apontar `@source` pro `dist` gerado (um artefato, não versionado, que muda de forma a cada build) em vez de pro código fonte estável — frágil e sem necessidade nenhuma, já que os bundlers dos apps já sabem transpilar `.tsx` de um pacote workspace de graça.

**Por que `src/styles.css` não importa `'tailwindcss'`** (a mesma pergunta, do lado do CSS): o comentário no topo do próprio arquivo já registra isso, mas vale repetir aqui porque é fácil "corrigir" isso por engano achando que falta um import. É o `@import 'tailwindcss'` que dispara o scanner de conteúdo do Tailwind v4 — e a **raiz** que esse scanner usa pra auto-detecção é resolvida a partir de **onde esse `@import` está**. Se `packages/ui/src/styles.css` importasse `'tailwindcss'` diretamente, a raiz de scan ficaria presa ao contexto deste pacote (que não sabe nada sobre `apps/web` nem `apps/financas/web`) em vez do contexto do app consumidor — exatamente o app que precisa controlar, via o próprio `@source`, quais diretórios entram no scan. `styles.css` deste pacote é uma **partial**: só tokens, variantes e a sentinela do gate. Quem importa `'tailwindcss'` — e portanto quem "possui" o scan — é sempre o CSS de entrada do app (`apps/web/app/globals.css`, `apps/financas/web/src/styles.css`), que faz `@import 'tailwindcss'` seguido de `@import '@piluvitu/ui/styles.css'` e só então declara o próprio `@source`.

## Estrutura

- **Sem barrel `index.ts` — um export por arquivo.** Um barrel forçaria qualquer bundler a puxar os 14 componentes pra usar 1 só; o `apps/financas/web` (Task 4) vai consumir poucos. `package.json` → `exports` mapeia cada subpath (`@piluvitu/ui/button`, `/card`, `/badge`, …) direto pro `.tsx` cru em `src/` — nada é pré-compilado/emitido (`"noEmit": true` no `tsconfig.json`; o bundler de cada app consumidor faz a transpilação).
- **`src/cn.ts`** — `cn()` (clsx + tailwind-merge). Guarda o comentário-sentinela do gate (`scripts/check-tailwind-source.mjs`, raiz) — nunca apagar, nunca copiar o literal pra dentro de nenhum `apps/*` (nem em doc): ver `SENTINEL_SELECTOR` no script.
- **`src/styles.css`** — tokens do Design System V2 (`@theme`, `:root`/`.dark`) + a `@utility` da sentinela.
- **Os 14 componentes** (`aspect-ratio`, `avatar`, `badge`, `button`, `card`, `command`, `dialog`, `dropdown-menu`, `form`, `input`, `label`, `separator`, `skeleton`, `textarea`) — imports internos entre eles são **relativos** (`./cn`, `./dialog`, `./label`), nunca via `@piluvitu/ui/...` (evita resolver o próprio pacote via `node_modules`).
- **`ajuda.tsx`** — `<Ajuda rotulo="Competência">conteúdo</Ajuda>`, gatilho "?" que abre um popover explicativo. **Não é shadcn** — construído direto sobre `@radix-ui/react-popover` porque o dono pediu "tooltip" mas registra despesas do **Android**, onde `hover` não existe: Tailwind emite `hover:` dentro de `@media (hover: hover)`, e essa mecânica já causou uma regressão real neste projeto (link de nav some no toque, sobra só cor a 1.99:1 de contraste — pego em review). Um tooltip (`@radix-ui/react-tooltip` ou `title=`) ficaria mudo pro dono; `Popover` abre no clique/tap e se comporta igual em Android e macOS. **Nunca trocar por tooltip nem por `title=`** (`title` tem o mesmo problema de hover _e_ é inconsistente pra leitor de tela). Acessibilidade: o gatilho é um `<button type="button">` com `aria-label` derivado de `rotulo` (`Ajuda sobre ${rotulo}`) — um "?" sem label não anuncia nada útil; `Esc` fecha (comportamento nativo do `Dismissable Layer` do Radix, não precisou de handler próprio). Versão do Radix: `@radix-ui/react-popover@^1.1.15` — fixada no mesmo valor exato que `@radix-ui/react-dialog` (o primitive mais próximo já no pacote) em vez de resolver a mais nova disponível, pra evitar skew entre cópias dos internals do Radix (`@radix-ui/react-context` etc.) que compound components dependem via identidade de contexto React. Nenhum dos dois apps consumidores importa `Ajuda` ainda (fica pra quem for colocar o componente nas telas) — **medido**: `grep -rl react-popover` nos builds de produção de `apps/web` (`.next`) e `apps/financas/web` (`dist`) não encontra nada, ou seja, zero impacto de bundle enquanto não for importado (nem o `exports` map nem a dependency instalada forçam inclusão — só um `import` de verdade faz o bundler puxar o código).
- ⚠️ **`button.tsx` — `cursor-pointer` (fix round 1, achado da Task 9 do financas) faltava na string base do `buttonVariants` (`cva`).** As antigas 58 linhas de CSS à mão de `apps/financas/web` (`button { cursor: pointer }`) escondiam essa lacuna; quando essa SPA migrou pro componente `Button` de verdade, o cursor default do navegador (não a mãozinha de clique) apareceu em todo botão — e como o componente é **compartilhado**, `apps/web` também estava exposto, só que ninguém tinha notado porque nenhuma das telas de lá dependia de um `button` cru pra comparar. Corrigido acrescentando `cursor-pointer` à string base — `disabled:pointer-events-none` (já presente) continua bloqueando o clique no estado desabilitado independente do ícone do cursor. `apps/web` (jest + tsc) reexecutado depois da mudança — verde, sem teste dependente do cursor. Este é o único rendered-CSS change que `apps/web` herda deste branch de design system além do que já era esperado — ver a nota M3 em `apps/web/CLAUDE.md`.
  - **M2 (fix final):** o comentário acima da string base alegava que `disabled:cursor-not-allowed` também cobria o estado desabilitado — essa classe nunca esteve na string do `cva`. O comportamento sempre esteve certo (`disabled:pointer-events-none`, que já bloqueia o clique, é suficiente — o cursor do estado desabilitado fica o default do navegador, nunca foi um requisito à parte); só o comentário afirmava uma classe que não existia. Reescrito pra não alegar o que o código não faz.
- **`sonner.tsx` NÃO mora aqui** — fica em `apps/web/components/ui/sonner.tsx` porque é o único componente acoplado a `next-themes` (`useTheme()`); trazê-lo obrigaria o pacote a carregar um provider que a SPA do finanças (Vite, sem `next-themes`) não tem como suprir. Ele importa `cn` de `@piluvitu/ui/cn` como os demais.

## Dependências

`react` é **peerDependency** (`^19.2.4` — cada app consumidor traz sua própria cópia). Os Radix primitives, `class-variance-authority`, `clsx`, `cmdk`, `react-hook-form` e `tailwind-merge` são **dependencies** diretas do pacote, nas mesmas versões que `apps/web` já usava antes da migração (conferir contra `apps/web/package.json` ao bumpar). `@radix-ui/react-popover@^1.1.15` (dep. de `ajuda.tsx`) segue a mesma regra — copiada do valor exato de `@radix-ui/react-dialog`, não resolvida fresh. `@types/react` é **devDependency** — necessário pro `tsc` de qualquer consumidor conseguir checar os `.tsx` crus deste pacote (sem isso, `React.HTMLAttributes`/JSX ficam `any` silenciosamente em quem importa). Nenhuma dessas adições precisou de `allowBuilds` — nenhuma delas tem lifecycle script de instalação.

## Testes

`cn.test.ts` (lógica pura) e `ajuda.test.tsx` (primeiro teste de componente React do pacote, `@testing-library/react` + `userEvent.click`/`.hover()`) — `jest` + `jest-environment-jsdom`, config em `jest.config.ts`. Os 14 componentes shadcn **nunca tiveram** `.test.tsx`/`.stories.tsx` próprios em `apps/web/components/ui/` — a migração não criou nenhum (lei de colocation não foi violada: não havia o que colocar). Se algum componente ganhar teste/story no futuro, colocation vale aqui também (`button.tsx` → `button.test.tsx`/`button.stories.tsx` dentro de `src/`).

**O que `ajuda.test.tsx` mudou na infra de teste do pacote** (nada disso existia antes, porque `cn.test.ts` é lógica pura sem DOM):

- `jest.config.ts` → `testMatch` ganhou `**/*.test.tsx` (só tinha `.test.ts`) e `setupFilesAfterEnv: ['<rootDir>/jest.setup.ts']`.
- `jest.setup.ts` (novo, raiz do pacote, mesmo padrão de `apps/web/jest.setup.ts`) → `import '@testing-library/jest-dom'`, registra os matchers (`toBeInTheDocument` etc.) em runtime.
- `tsconfig.json` → `include` ganhou `"jest.setup.ts"` além de `src/**`. **Por quê:** o pacote deliberadamente restringe `include` a `src/**` (só o que é de fato publicado via `exports`) — mas a augmentation de tipos do `@testing-library/jest-dom` (que dá tipo a `toBeInTheDocument` etc.) só existe pro `tsc` se o arquivo que faz `import '@testing-library/jest-dom'` estiver dentro do programa TS. Sem essa entrada, `pnpm test` passava (o `ts-jest` deste pacote não faz type-check completo por arquivo) mas `tsc --noEmit` reclamava de `toBeInTheDocument`/`toHaveAttribute` não existirem no tipo do matcher — pego antes do commit.
- Novas devDependencies: `@testing-library/react`, `@testing-library/jest-dom`, `@testing-library/user-event` (mesmas versões de `apps/financas/web/package.json`, único outro workspace que já as usava — `16.3.0`/`6.9.1`/`14.6.1`) + `react-dom` e `@types/react-dom` (só pra rodar/tipar teste; `react-dom` **não** virou `dependency` nem `peerDependency` do pacote — cada consumidor já traz a própria cópia).
- **Regra de teste pra qualquer componente baseado em Radix "abre/fecha":** testar com `userEvent.click`, nunca `mouseOver` — um `mouseOver` passaria contra um Tooltip _e_ contra um Popover, não prova qual dos dois foi implementado. Assertar que o conteúdo **não está no DOM antes de abrir** (`queryByText` retorna `null`) — senão um componente que renderiza tudo sempre e só esconde via CSS também passaria.

- **Rodar:** `pnpm --filter @piluvitu/ui test` ou `pnpm -r test` / `make test` na raiz.
- **Não roda no `ci.yml`** hoje (só `apps/web` e `packages/tools` têm step de teste dedicado) — gap conhecido, não fechado nesta task; ver "Concerns" do report da Task 3.

## Lint

`eslint.config.mjs` **próprio** do pacote — não estende o de `apps/web` (que é Next-specific: `@next/eslint-plugin-next`, `@tanstack/eslint-plugin-query`, `eslint-plugin-storybook`, nenhum dos quais faz sentido aqui). Cobre `eslint-plugin-react` + `eslint-plugin-react-hooks` (`rules-of-hooks`, `exhaustive-deps`) + `@typescript-eslint/no-unused-vars` + um subconjunto de `eslint-plugin-jsx-a11y`.

**Por que um subconjunto de a11y, não o `recommended` inteiro do plugin:** o `recommended` completo inclui `jsx-a11y/heading-has-content`, que dá falso positivo em componentes `forwardRef` cujo `children` só chega via props/spread (`CardTitle`, `<h3 {...props} />`) — nunca aparece como filho JSX literal. O subconjunto usado (`alt-text`, `aria-props`, `aria-proptypes`, `aria-unsupported-elements`, `role-has-required-aria-props`, `role-supports-aria-props`) e o override `react/no-unknown-property: off` (o atributo customizado `cmdk-input-wrapper` de `command.tsx`) são **exatamente** os que `eslint-config-next/index.js` já aplicava a estes arquivos antes do move — o objetivo é restaurar a cobertura que existia, não inventar regra nova que os arquivos já existentes nunca passaram por.

**Antes desta correção, `pnpm -r lint` pulava `packages/ui` silenciosamente** (workspace sem script `lint` → `pnpm -r` simplesmente não roda nada nele, sem erro, sem aviso — a mesma armadilha que o `CLAUDE.md` da raiz já documenta pra outros contextos). Os 14 componentes ficaram sem `react-hooks/rules-of-hooks`, `exhaustive-deps`, `no-unused-vars` ou a11y verificados por um tempo depois da Task 3 até este fix. Prova de que a regra pega de verdade (não é um script que "passa" porque não linta nada): um import não usado (`@typescript-eslint/no-unused-vars`) e um hook chamado condicionalmente (`react-hooks/rules-of-hooks`) foram introduzidos de propósito num componente, confirmados como `error`/exit 1, e revertidos.

- **Rodar:** `pnpm --filter @piluvitu/ui lint` ou `pnpm -r lint` / `make lint` na raiz.
- **Amarrado em `ci.yml`:** step "Lint (ui package)" no job `web`.

## Gate do design system: `@source`, o sentinela, e a assimetria dev/prod

Ver também "Gate do design system" no `CLAUDE.md` da raiz (visão geral do script). Aqui fica a história completa — em particular a armadilha que qualquer pessoa nova vai pisar se testar só em dev.

**O que `@source` faz e por que é obrigatório.** Tailwind v4 é CSS-first: a auto-detecção de conteúdo do scanner tem uma RAIZ, resolvida a partir de onde `@import 'tailwindcss'` está — por padrão essa raiz é o próprio diretório do app consumidor (e tudo abaixo dele, exceto o que o `.gitignore` esconde). `packages/ui/src` fica **fora** dessa raiz nos dois apps (é um pacote irmão, não um subdiretório do app) — sem um `@source '<caminho para packages/ui/src>'` explícito no CSS de entrada do app, o scanner nunca abre esses arquivos, e toda classe Tailwind usada **exclusivamente** dentro de `packages/ui` (não replicada em alguma classe que o próprio app já usa) é descartada do CSS final. Isso não quebra o build — nenhum erro, nenhum warning —, os componentes compartilhados só renderizam sem estilo em produção.

**O sentinela.** `packages/ui/src/styles.css` define `@utility ui-sentinela-nao-remover`, nunca usada por nenhum componente real — existe só para o gate. Ela só aparece no CSS emitido se o scanner alcançar o literal `ui-sentinela-nao-remover`, que mora **só** num comentário em `packages/ui/src/cn.ts` (nunca como string executada em runtime). `scripts/check-tailwind-source.mjs` (raiz) procura essa classe no CSS de build: ausência ⇒ `@source` errado ou faltando; presença ⇒ certo. Amarrado no `build` (e `build:ci`) dos dois apps — **nunca no `dev`**, e o bullet abaixo é o motivo.

⚠️ **NUNCA escreva o nome da sentinela por extenso dentro de `apps/*` — nem em documentação, nem em comentário.** A auto-detecção do Tailwind v4 varre todo arquivo não-ignorado da árvore do app, inclusive `.md`, **independente de `@source`**. Escrever o literal ali faz o Tailwind gerar a classe sozinho — e o gate passa a aprovar builds com `@source` quebrado, porque ele deixa de medir qualquer coisa. Já aconteceu de verdade: `apps/web/CLAUDE.md`, na Task 2 deste mesmo plano — a documentação que explicava o gate foi o que o neutralizou, pego só na revisão. Em qualquer doc, referencie `SENTINEL_SELECTOR` (a constante no topo do script), nunca o literal.

**A assimetria dev/prod, MEDIDA nesta task (Task 11), não presumida** — comentei o `@source` de cada app, subi o dev server real, conferi o CSS servido, restaurei:

- **Vite (`apps/financas/web`) MENTE em dev.** Com `@source` comentado em `src/styles.css` e `pnpm --filter @piluvitu/financas-web dev` (porta 5273) no ar, o CSS servido em `/src/styles.css` continha classes reais de `packages/ui` — `.bg-primary`, `.border-input`, `.hover\:bg-primary\/90`, `.disabled\:opacity-50`, `.focus-visible\:ring-1` (todas de `button.tsx`/`input.tsx`) — a tela parece normal. Só a sentinela (que só existe como comentário em `cn.ts`, nunca como string em runtime) veio ausente. Motivo: o plugin Vite do Tailwind v4 usa o **grafo de módulos do próprio Vite** pra detecção incremental em dev — qualquer arquivo que o Vite de fato transforma como parte da árvore de imports real (aqui, `button.tsx`/`input.tsx`/`card.tsx`, importados de verdade pela SPA) entra no scan, `@source` ou não. É uma conveniência do dev server, não o mecanismo de produção — e por isso um comentário (nunca transformado/executado como string) não entra.
- **Vite só conta a verdade no `build`.** Já medido na Task 4 (ver bullet acima): `vite build` sem `@source` produz um CSS bem menor (6,32 kB vs. 24,24 kB com `@source`) — o build usa os content roots explícitos do `@source`, não o grafo de módulos do dev server, e é aí que as classes desaparecem de verdade.
- **Next (`apps/web`) NÃO mente nem em dev.** Mesmo teste: `@source` comentado em `app/globals.css`, `pnpm --filter @piluvitu/web dev` (webpack, porta 3333) no ar — o CSS servido (`/_next/static/css/app/layout.css`) já saiu sem a sentinela, e ~450 linhas mais curto (3291 vs. 3740 linhas com `@source`). Restaurando o `@source` (sem reiniciar o servidor — só um novo request, o dev do Next já recompila o CSS sozinho), a sentinela volta. O webpack do Next não empresta ao dev o mesmo grafo-de-módulos-como-scanner que o Vite empresta ao seu.

**Por que isso importa pra quem mexer no pacote depois:** testar só `apps/financas/web` com `pnpm --filter @piluvitu/financas-web dev` deixa um `@source` quebrado passar despercebido — a tela parece certa. `apps/web` avisa até em dev; `apps/financas/web` só avisa no `build`. É exatamente por isso que o gate está amarrado no `build` (nunca no `dev`) dos dois apps — `pnpm --filter @piluvitu/financas-web run build` (que builda e roda o gate em sequência) é o comando que de fato prova que o pacote está sendo consumido certo; o dev server rodando sem erro não prova nada nesse app.

## Dependency policy

Adição de deps segue a política da raiz (pnpm ≥ 11, `allowBuilds`, `minimumReleaseAge`). Ao trocar a versão de um Radix primitive ou do `react-hook-form` aqui, sincronizar com `apps/web/package.json` (hoje as duas árvores de deps são independentes — nada garante que fiquem em sync automaticamente).
