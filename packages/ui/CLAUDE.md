# CLAUDE.md — `packages/ui` (`@piluvitu/ui`)

Guidance for the **shared design system package**. O Claude Code carrega este arquivo **junto** com o `CLAUDE.md` da raiz. Consumido por `apps/web` (Task 3 do plano `docs/superpowers/plans/2026-07-26-financas-ui-design-system.md`) e, desde a Task 4, por `apps/financas/web` (SPA Vite) — ver `apps/financas/CLAUDE.md` § _SPA_ para os detalhes do lado Vite.

## Propósito

`@piluvitu/ui` centraliza o **design system** compartilhado: tokens (cores, radius, fontes, keyframes — `src/styles.css`), o helper `cn()`, os **14 componentes shadcn/ui** (New York style, sobre Radix primitives) que eram exclusivos de `apps/web/components/ui/`, e componentes **não-shadcn** construídos direto sobre Radix primitives quando o caso de uso pede (ver `ajuda.tsx` abaixo).

## Por que não tem build

Não existe `dist/`, não existe passo de compilação — `tsconfig.json` tem `"noEmit": true`, e `package.json` → `exports` mapeia cada subpath (`@piluvitu/ui/button`, `/card`, …) direto pro `.tsx`/`.ts` **cru** dentro de `src/`. Os dois consumidores (`apps/web` via webpack/Turbopack, `apps/financas/web` via Vite) importam esse código fonte e cada bundler faz a própria transpilação — **medido** nas Tasks 2/3/4: nem CSS (`@import`/`@source`) nem os `.tsx` (incl. `'use client'`, JSX, `React.forwardRef`) precisam de `transpilePackages: ['@piluvitu/ui']` no `next.config.mjs`, nem de configuração equivalente no `vite.config.ts` — os dois bundlers resolvem um pacote workspace pnpm sem build próprio sem problema.

Isso não é só "menos trabalho" — é **necessário** pro `@source` funcionar (ver seção _Gate do design system_ mais abaixo). O scanner de conteúdo do Tailwind v4 procura classes em **texto-fonte**, no diretório que o `@source` aponta (`packages/ui/src`). Se este pacote publicasse um `dist/` pré-compilado/minificado em vez do `.tsx` cru, os dois apps consumidores precisariam apontar `@source` pro `dist` gerado (um artefato, não versionado, que muda de forma a cada build) em vez de pro código fonte estável — frágil e sem necessidade nenhuma, já que os bundlers dos apps já sabem transpilar `.tsx` de um pacote workspace de graça.

**Por que `src/styles.css` não importa `'tailwindcss'`** (a mesma pergunta, do lado do CSS): o comentário no topo do próprio arquivo já registra isso, mas vale repetir aqui porque é fácil "corrigir" isso por engano achando que falta um import. É o `@import 'tailwindcss'` que dispara o scanner de conteúdo do Tailwind v4 — e a **raiz** que esse scanner usa pra auto-detecção é resolvida a partir de **onde esse `@import` está**. Se `packages/ui/src/styles.css` importasse `'tailwindcss'` diretamente, a raiz de scan ficaria presa ao contexto deste pacote (que não sabe nada sobre `apps/web` nem `apps/financas/web`) em vez do contexto do app consumidor — exatamente o app que precisa controlar, via o próprio `@source`, quais diretórios entram no scan. `styles.css` deste pacote é uma **partial**: só tokens, variantes e a sentinela do gate. Quem importa `'tailwindcss'` — e portanto quem "possui" o scan — é sempre o CSS de entrada do app (`apps/web/app/globals.css`, `apps/financas/web/src/styles.css`), que faz `@import 'tailwindcss'` seguido de `@import '@piluvitu/ui/styles.css'` e só então declara o próprio `@source`.

## Estrutura

- **Sem barrel `index.ts` — um export por arquivo.** Um barrel forçaria qualquer bundler a puxar os 14 componentes pra usar 1 só; o `apps/financas/web` (Task 4) vai consumir poucos. `package.json` → `exports` mapeia cada subpath (`@piluvitu/ui/button`, `/card`, `/badge`, …) direto pro `.tsx` cru em `src/` — nada é pré-compilado/emitido (`"noEmit": true` no `tsconfig.json`; o bundler de cada app consumidor faz a transpilação).
- **`src/cn.ts`** — `cn()` (clsx + tailwind-merge). Guarda o comentário-sentinela do gate (`scripts/check-tailwind-source.mjs`, raiz) — nunca apagar, nunca copiar o literal pra dentro de nenhum `apps/*` (nem em doc): ver `SENTINEL_SELECTOR` no script.
- **`src/styles.css`** — tokens do Design System V2 (`@theme`, `:root`/`.dark`) + a `@utility` da sentinela. ⚠️ A LUMINOSIDADE dos tokens de cor do bloco `:root` é fixada por medição WCAG, não por gosto — ver § _Contraste dos tokens_ abaixo antes de clarear qualquer um deles.
- **`src/contraste.ts`** — lógica pura de contraste WCAG (HSL→RGB, luminância relativa, razão, parser de `:root`/`.dark`), consumida só pelo gate `contraste.test.ts` ao lado. Fora do `exports` de propósito: é ferramenta de teste, não API do design system.
- **Os 14 componentes "clássicos"** (`aspect-ratio`, `avatar`, `badge`, `button`, `card`, `command`, `dialog`, `dropdown-menu`, `form`, `input`, `label`, `separator`, `skeleton`, `textarea`) — imports internos entre eles são **relativos** (`./cn`, `./dialog`, `./label`), nunca via `@piluvitu/ui/...` (evita resolver o próprio pacote via `node_modules`).
- **`chart.tsx`** (Task 1, fatia ⑨ — 15º componente shadcn) — vendorizado direto do registry shadcn/ui (`chart.tsx`, new-york), adaptado só no import de `cn` (`@/lib/utils` → `./cn`) e no `'use client'` no topo (consistente com `dialog.tsx`/`dropdown-menu.tsx`/`ajuda.tsx`, os outros componentes interativos do pacote) — lógica intocada. Exporta `ChartContainer`, `ChartTooltip`/`ChartTooltipContent`, `ChartLegend`/`ChartLegendContent`, `ChartStyle` e o tipo `ChartConfig`.
  - **É construído sobre `recharts`** — a única dependência deste pacote que NÃO é Radix/utilitário puro. `recharts@^3.10.1`, copiada do valor exato que `apps/financas/web/package.json` já declarava (mesma regra de nunca resolver fresh — ver § _Dependências_) — a única consumidora de `recharts` hoje é `apps/financas/web`.
  - ⚠️ **`ChartContainer` embute `RechartsPrimitive.ResponsiveContainer` — quem for TESTAR um componente que o usa precisa saber de um efeito colateral MEDIDO nesta task.** `ResponsiveContainer`, quando existe um `ResizeObserver` GLOBAL no ambiente de teste, ignora o `initialDimension` (fallback default do shadcn, 320×200) assim que o primeiro callback do observer dispara — e QUALQUER stub de `ResizeObserver` que não preencha `contentRect.height` (ex.: um stub feito só pra medir `clientWidth`, como `apps/financas/web/src/test/setup.ts` já tinha antes desta task, pros outros dois gráficos daquele app) faz `ResponsiveContainer` computar `containerHeight: NaN` e não renderizar NADA (guarda `isAcceptableSize`). `packages/ui/jest.setup.ts` **não** define `ResizeObserver` global nenhum — é por isso que `chart.test.tsx` (aqui) não precisou de nenhum mock: sem `ResizeObserver`, `SizeDetectorContainer` (recharts) toma o caminho de early-return e mantém o `initialDimension` fallback, não-zero, renderizável. Um consumidor com `ResizeObserver` global (caso de `apps/financas/web`) precisa ou mockar/remover o `ResizeObserver` global só durante o teste do componente que usa `ChartContainer`, ou garantir que o stub preenche altura E largura — ver `apps/financas/web/src/blocos/GraficoComprometido.test.tsx`, describe de `GraficoFluxo`, pro caso resolvido.
  - **Cor por `ChartConfig`, nunca hex** — cada série declara `color` (ou `theme: {light, dark}` pra cores que mudam por tema) e `ChartStyle` injeta um `<style>` com `--color-<chave>: <valor>` escopado a `[data-chart=<id>]`; os elementos do gráfico consomem via `var(--color-<chave>)`. `packages/ui/src/styles.css` ganhou `--chart-1`..`--chart-5` (light + dark, dentro de `@layer base`, e mapeados em `@theme` como `--color-chart-N` pra quem quiser as classes utilitárias `bg-chart-1`/etc.) — paleta NEUTRA reaproveitando os mesmos matizes de `--success`/`--warn`/`--win` (nenhuma cor nova), pra série sem significado de risco/status (diferente de `--primary`/`--destructive`, já carregados de sentido: azul = normal, vermelho = alerta em outras telas). `--chart-1` reflete `--primary` de propósito — é a cor default de um gráfico com série única (ex. o acumulado do fluxo de caixa). ⚠️ **CORREÇÃO: esse espelhamento vale só no `.dark` hoje.** A fatia de contraste escureceu `--primary` no `:root` e NÃO tocou nos `--chart-*` (série de gráfico tem outro mínimo, e mudar a paleta é decisão de data-viz) — no tema claro os dois divergem, e três das cinco séries ficam abaixo de 3:1. Ver § _Contraste dos tokens_.
  - **Consumo real, medido:** `apps/financas/web/src/blocos/GraficoComprometido.tsx#GraficoFluxo` (área do acumulado no fluxo de caixa) — ver `apps/financas/CLAUDE.md` § _Mapa de fluxo de caixa_ pro detalhe do consumidor e a prova de que `recharts`/`@piluvitu/ui/chart` continuam atrás da MESMA fronteira lazy (nenhum chunk novo). `apps/web` não importa `chart.tsx` — **zero impacto de JS** (`grep -rl recharts .next/static/chunks/*.js` não encontra nada, MEDIDO depois desta task), mas **não zero impacto de CSS**, ao contrário do que `ajuda.tsx` tinha estabelecido como precedente: `chart.tsx` tem classes `[&_.recharts-cartesian-axis-tick_text]:...` (variantes arbitrárias citando seletores `.recharts-*`) na string base de `ChartContainer`, e o scanner do Tailwind varre TEXTO em `packages/ui/src` inteiro via `@source`, independente de import — essas classes viram CSS de verdade no build de `apps/web` mesmo sem `chart.tsx` nunca ser importado lá (MEDIDO: 36 ocorrências do substring `recharts` no CSS compilado de produção). É CSS **inerte** (nenhum elemento `.recharts-*` existe no DOM de `apps/web`, que não renderiza gráfico nenhum), mesma categoria de "custo" que qualquer classe exclusiva de outro componente shadcn que `apps/web` também não usa — não é regressão nem motivo de alarme, só a mecânica já documentada em § _Gate do design system_ se aplicando a mais uma superfície de string.
- **`sheet.tsx`** (fatia da casca de `apps/financas`) — painel ancorado numa BORDA da tela (`side="top|bottom|left|right"`, `cva`), exportando `Sheet`/`SheetTrigger`/`SheetContent`/`SheetHeader`/`SheetFooter`/`SheetTitle`/`SheetDescription`/`SheetClose`/`SheetOverlay`/`SheetPortal` + `sheetVariants`.
  - ⚠️ **NÃO é um primitive novo: é o MESMO `@radix-ui/react-dialog` de `dialog.tsx`**, que já era dependência declarada deste pacote. O custo marginal medido no consumidor é ~0,5 kB gzip (o `cva` das quatro variantes + o markup) — não uma segunda família de internals do Radix. Toda a semântica que importa (foco preso, `Esc` fecha, `aria-modal`, restauração de foco no gatilho) vem do primitive.
  - **`side="bottom"` é o caso de uso que motivou o arquivo** (o menu "Mais" de `apps/financas/web`): num celular, um menu de navegação precisa nascer perto do polegar, não no meio da tela. As outras três direções vêm do `cva` do shadcn original — removê-las não economizaria nada mensurável e faria o componente divergir do upstream.
  - ⚠️ **`Sheet` NÃO emite `menuitem`** (ao contrário de `dropdown-menu.tsx`): o conteúdo é um `role="dialog"` com o que você puser dentro. Quem migrar de `dropdown-menu` pra `Sheet` precisa trocar toda asserção de `menuitem` por `dialog` + o role real do item (`link`, `button`) — foi exatamente o que a casca do finanças teve que fazer.
  - **`SheetClose` tem `<span className="sr-only">Fechar</span>`** (em português, não "Close" como o `dialog.tsx` que ele copia): os dois consumidores possíveis deste componente hoje são telas em pt-BR, e um botão "×" sem nome acessível não anuncia nada.
- **`ajuda.tsx`** — `<Ajuda rotulo="Competência">conteúdo</Ajuda>`, gatilho "?" que abre um popover explicativo. **Não é shadcn** — construído direto sobre `@radix-ui/react-popover` porque o dono pediu "tooltip" mas registra despesas do **Android**, onde `hover` não existe: Tailwind emite `hover:` dentro de `@media (hover: hover)`, e essa mecânica já causou uma regressão real neste projeto (link de nav some no toque, sobra só cor a 1.99:1 de contraste — pego em review). Um tooltip (`@radix-ui/react-tooltip` ou `title=`) ficaria mudo pro dono; `Popover` abre no clique/tap e se comporta igual em Android e macOS. **Nunca trocar por tooltip nem por `title=`** (`title` tem o mesmo problema de hover _e_ é inconsistente pra leitor de tela). Acessibilidade: o gatilho é um `<button type="button">` com `aria-label` derivado de `rotulo` (`Ajuda sobre ${rotulo}`) — um "?" sem label não anuncia nada útil; `Esc` fecha (comportamento nativo do `Dismissable Layer` do Radix, não precisou de handler próprio). ⚠️ **Área de toque de 44×44 sobre um círculo que continua com 20×20** (fatia a11y de `apps/financas`): MEDIDO em Chrome real a 390×844, o gatilho tinha 20×20 px em 10 telas — metade do lado recomendado (Apple HIG / WCAG 2.5.5), e o dono usa o app num Android, muitas vezes sob sol. Crescer o CÍRCULO seria pior (ele mora colado a títulos e rótulos, e viraria o elemento mais pesado da linha), então quem cresce é só a caixa clicável, via pseudo-elemento absoluto centrado (`after:h-11 after:w-11 after:-translate-x-1/2 after:-translate-y-1/2`) — `position: absolute` não ocupa espaço no fluxo, logo **nenhum layout mudou**. Provado por toque REAL (`page.touchscreen.tap` a 18 px acima do centro, fora do círculo ⇒ o popover abre) e por `elementFromPoint` nas 4 direções; `ajuda.test.tsx` trava as classes (mutação removendo o pseudo-elemento derruba 1 teste). ⚠️ Quem colocar `Ajuda` ao lado de outro controle precisa de pelo menos `gap-3`: a área avança 12 px pra cada lado do círculo, e com `gap-1` ela invadiria o vizinho — sobrepor alvo a alvo seria trocar um defeito de toque por outro (ver `debt-detail.tsx`, § _Acessibilidade de toque_ em `apps/financas/CLAUDE.md`, onde isso foi medido: as bordas encostam em 96,3 px, sem sobreposição).

Versão do Radix: `@radix-ui/react-popover@^1.1.15` — fixada no mesmo valor exato que `@radix-ui/react-dialog` (o primitive mais próximo já no pacote) em vez de resolver a mais nova disponível, pra evitar skew entre cópias dos internals do Radix (`@radix-ui/react-context` etc.) que compound components dependem via identidade de contexto React. Nenhum dos dois apps consumidores importa `Ajuda` ainda (fica pra quem for colocar o componente nas telas) — **medido**: `grep -rl react-popover` nos builds de produção de `apps/web` (`.next`) e `apps/financas/web` (`dist`) não encontra nada, ou seja, zero impacto de bundle enquanto não for importado (nem o `exports` map nem a dependency instalada forçam inclusão — só um `import` de verdade faz o bundler puxar o código).

- ⚠️ **`button.tsx` — `cursor-pointer` (fix round 1, achado da Task 9 do financas) faltava na string base do `buttonVariants` (`cva`).** As antigas 58 linhas de CSS à mão de `apps/financas/web` (`button { cursor: pointer }`) escondiam essa lacuna; quando essa SPA migrou pro componente `Button` de verdade, o cursor default do navegador (não a mãozinha de clique) apareceu em todo botão — e como o componente é **compartilhado**, `apps/web` também estava exposto, só que ninguém tinha notado porque nenhuma das telas de lá dependia de um `button` cru pra comparar. Corrigido acrescentando `cursor-pointer` à string base — `disabled:pointer-events-none` (já presente) continua bloqueando o clique no estado desabilitado independente do ícone do cursor. `apps/web` (jest + tsc) reexecutado depois da mudança — verde, sem teste dependente do cursor. Este é o único rendered-CSS change que `apps/web` herda deste branch de design system além do que já era esperado — ver a nota M3 em `apps/web/CLAUDE.md`.
  - **M2 (fix final):** o comentário acima da string base alegava que `disabled:cursor-not-allowed` também cobria o estado desabilitado — essa classe nunca esteve na string do `cva`. O comportamento sempre esteve certo (`disabled:pointer-events-none`, que já bloqueia o clique, é suficiente — o cursor do estado desabilitado fica o default do navegador, nunca foi um requisito à parte); só o comentário afirmava uma classe que não existia. Reescrito pra não alegar o que o código não faz.
- **`sonner.tsx` NÃO mora aqui** — fica em `apps/web/components/ui/sonner.tsx` porque é o único componente acoplado a `next-themes` (`useTheme()`); trazê-lo obrigaria o pacote a carregar um provider que a SPA do finanças (Vite, sem `next-themes`) não tem como suprir. Ele importa `cn` de `@piluvitu/ui/cn` como os demais.

## Contraste dos tokens (WCAG) — `contraste.ts` + `contraste.test.ts`

**O tema CLARO chegou à produção reprovando AA, e nada no repositório media isso.** Medido (WCAG 2.1, sobre `--card`, antes da correção): `--primary` **2,10:1**, `--destructive` **3,78:1**, `--success`/`--ok` **3,06:1**, `--warn` **3,61:1** — todos abaixo dos 4,5:1 de texto, e o `--primary` abaixo até dos 3:1 de componente gráfico. O alcance é o pior possível: `text-primary` é todo link (inclusive o ÚNICO caminho para abrir uma dívida em `apps/financas/web`), `text-destructive` são 19 `role="alert"` só no finanças, e o dono usa o app **num Android, muitas vezes sob sol**. O tema `.dark` sempre passou com folga (mínimo 6,68:1) e **não foi tocado**.

**Corrigido só no bloco `:root`**, escurecendo o valor sem mexer no matiz (a identidade é o H, não o L):

Com o `--primary` escuro, um texto quase preto em cima dele dá **3,77:1** — trocar um por outro sem trocar o par apenas move a reprovação de lugar. ⚠️ **`--ring` acompanha `--primary` (sempre foi um espelho dele).** Um anel de foco a 2,00:1 sobre o fundo é invisível, e o mínimo de componente de interface é 3:1 — hoje 7,09.

⚠️ **`--chart-1..5` NÃO foram tocados, e a consequência fica dita: `--chart-1` era um espelho de `--primary` e deixou de ser no tema claro.** Série de gráfico é componente gráfico (3:1), não texto (4,5:1), e a paleta é deliberadamente neutra — escurecê-la é decisão de data-viz, não efeito colateral. Medido sobre `--background`, tema claro: chart-1 2,00 · chart-2 2,89 · chart-3 2,03 · chart-4 4,60 · chart-5 3,98 (**três abaixo de 3:1** — pendência registrada, não corrigida). `contraste.test.ts` não cobre esses tokens.

⚠️ **A hierarquia `--primary` × `--destructive` PIOROU um pouco, e isso é inerente: 1,80 → 1,48 no claro** (escuro 1,31, intocado). O teste trava um piso de 1,2 entre os dois: impede que a aproximação vire colapso.

### O gate: `src/contraste.test.ts` — e por que ele mora AQUI, não num app

`src/contraste.ts` é lógica pura (HSL→RGB, luminância relativa, razão de contraste, parser dos blocos `:root`/`.dark`); o teste colocado ao lado LÊ `src/styles.css` — o arquivo de verdade, nunca uma cópia dos valores — e falha se qualquer token de texto cair abaixo de 4,5:1 no tema em que é usado. Não é exportado em `package.json#exports`: é gate, não API do design system.

**Três motivos para morar em `packages/ui`, e não em `apps/web`/`apps/financas/web`:**

1. **É onde o token vive.** Os dois apps só consomem `@piluvitu/ui/styles.css` — um gate dentro de um app mediria a cor dos dois a partir de um deles, e o outro passaria a depender de um teste que não é dele. Mudar `--primary` muda os DOIS (medido: 56 ocorrências de `text-primary`/`text-destructive` em `apps/web`, 72 no finanças).
2. **Ele roda de fato no CI.** `packages/ui` declara `test` no `package.json` **e** tem step dedicado em `ci.yml` (job `web` → "Test (ui package)"), com `--filter` explícito justamente porque `pnpm -r test` pula em silêncio quem não declara o script — a armadilha que já deixou este pacote sem `lint` por um tempo.
3. **Colocation é lei do projeto:** `styles.css` e `contraste.test.ts` no mesmo diretório.

**O que o gate cobre** (os dois temas, sempre): todo token de texto (`foreground`, `muted-foreground`, `primary`, `destructive`, `success`, `ok`, `warn`, `win`) sobre `--card` **e** `--background`; todo par `--x-foreground` sobre `--x` — **descoberto pelo sufixo, nunca listado à mão**, então um par de token novo entra no gate sozinho; `--ring` contra os 3:1 de interface; o piso de 1,2 entre `--primary` e `--destructive`; `--ok` sendo alias exato de `--success`; e um piso de folga (6:1) no `.dark`, para "não regrida o tema que está certo" ser asserção em vez de recomendação — piso, nunca valor pinado (pinar convida a editar o teste junto com a paleta, que é como um gate deixa de ser gate).

⚠️ **O gate tem guarda anti-vacuidade, e ela não é decorativa:** o corpo é um `for` sobre o que o parser achou, então um parser quebrado devolvendo `{}` faria TUDO passar sem medir nada. Por isso existem asserções de que cada tema tem ≥30 tokens, que os nomes conhecidos parseiam como cor, e que 11 pares foreground/superfície foram descobertos em cada tema.

⚠️ **Comentários do CSS são removidos antes do parse.** As explicações dentro do `:root` citam tokens por nome ao registrar as medições antigas — uma delas escrita com dois-pontos seria lida como declaração e o gate mediria a cor errada. Provado por fixture sintética no teste (não pelo `styles.css` real, que hoje não tem esse formato — por isso o arquivo real não provaria nada aqui).

## Gate do design system: `@source`, o sentinela, e a assimetria dev/prod

Ver também "Gate do design system" no `CLAUDE.md` da raiz (visão geral do script). Aqui fica a história completa — em particular a armadilha que qualquer pessoa nova vai pisar se testar só em dev.

**O que `@source` faz e por que é obrigatório.** Tailwind v4 é CSS-first: a auto-detecção de conteúdo do scanner tem uma RAIZ, resolvida a partir de onde `@import 'tailwindcss'` está — por padrão essa raiz é o próprio diretório do app consumidor (e tudo abaixo dele, exceto o que o `.gitignore` esconde). `packages/ui/src` fica **fora** dessa raiz nos dois apps (é um pacote irmão, não um subdiretório do app) — sem um `@source '<caminho para packages/ui/src>'` explícito no CSS de entrada do app, o scanner nunca abre esses arquivos, e toda classe Tailwind usada **exclusivamente** dentro de `packages/ui` (não replicada em alguma classe que o próprio app já usa) é descartada do CSS final. Isso não quebra o build — nenhum erro, nenhum warning —, os componentes compartilhados só renderizam sem estilo em produção.

**O sentinela.** `packages/ui/src/styles.css` define `@utility ui-sentinela-nao-remover`, nunca usada por nenhum componente real — existe só para o gate. Ela só aparece no CSS emitido se o scanner alcançar o literal `ui-sentinela-nao-remover`, que mora **só** num comentário em `packages/ui/src/cn.ts` (nunca como string executada em runtime). `scripts/check-tailwind-source.mjs` (raiz) procura essa classe no CSS de build: ausência ⇒ `@source` errado ou faltando; presença ⇒ certo. Amarrado no `build` (e `build:ci`) dos dois apps — **nunca no `dev`**, e o bullet abaixo é o motivo.

⚠️ **NUNCA escreva o nome da sentinela por extenso dentro de `apps/*` — nem em documentação, nem em comentário.** A auto-detecção do Tailwind v4 varre todo arquivo não-ignorado da árvore do app, inclusive `.md`, **independente de `@source`**. Escrever o literal ali faz o Tailwind gerar a classe sozinho — e o gate passa a aprovar builds com `@source` quebrado, porque ele deixa de medir qualquer coisa. Já aconteceu de verdade: `apps/web/CLAUDE.md`, na Task 2 deste mesmo plano — a documentação que explicava o gate foi o que o neutralizou, pego só na revisão. Em qualquer doc, referencie `SENTINEL_SELECTOR` (a constante no topo do script), nunca o literal.

**A assimetria dev/prod, MEDIDA nesta task (Task 11), não presumida** — comentei o `@source` de cada app, subi o dev server real, conferi o CSS servido, restaurei:

- **Vite (`apps/financas/web`) MENTE em dev.** Com `@source` comentado em `src/styles.css` e `pnpm --filter @piluvitu/financas-web dev` (porta 5273) no ar, o CSS servido em `/src/styles.css` continha classes reais de `packages/ui` — `.bg-primary`, `.border-input`, `.hover\:bg-primary\/90`, `.disabled\:opacity-50`, `.focus-visible\:ring-1` (todas de `button.tsx`/`input.tsx`) — a tela parece normal. Só a sentinela (que só existe como comentário em `cn.ts`, nunca como string em runtime) veio ausente. Motivo: o plugin Vite do Tailwind v4 usa o **grafo de módulos do próprio Vite** pra detecção incremental em dev — qualquer arquivo que o Vite de fato transforma como parte da árvore de imports real (aqui, `button.tsx`/`input.tsx`/`card.tsx`, importados de verdade pela SPA) entra no scan, `@source` ou não. É uma conveniência do dev server, não o mecanismo de produção — e por isso um comentário (nunca transformado/executado como string) não entra.
- **Vite só conta a verdade no `build`.** Já medido na Task 4 (ver bullet acima): `vite build` sem `@source` produz um CSS bem menor (6,32 kB vs. 24,24 kB com `@source`) — o build usa os content roots explícitos do `@source`, não o grafo de módulos do dev server, e é aí que as classes desaparecem de verdade.
- **Next (`apps/web`) NÃO mente nem em dev.** Mesmo teste: `@source` comentado em `app/globals.css`, `pnpm --filter @piluvitu/web dev` (webpack, porta 3333) no ar — o CSS servido (`/_next/static/css/app/layout.css`) já saiu sem a sentinela, e ~450 linhas mais curto (3291 vs. 3740 linhas com `@source`). Restaurando o `@source` (sem reiniciar o servidor — só um novo request, o dev do Next já recompila o CSS sozinho), a sentinela volta. O webpack do Next não empresta ao dev o mesmo grafo-de-módulos-como-scanner que o Vite empresta ao seu.

**Por que isso importa pra quem mexer no pacote depois:** testar só `apps/financas/web` com `pnpm --filter @piluvitu/financas-web dev` deixa um `@source` quebrado passar despercebido — a tela parece certa. `apps/web` avisa até em dev; `apps/financas/web` só avisa no `build`. É exatamente por isso que o gate está amarrado no `build` (nunca no `dev`) dos dois apps — `pnpm --filter @piluvitu/financas-web run build` (que builda e roda o gate em sequência) é o comando que de fato prova que o pacote está sendo consumido certo; o dev server rodando sem erro não prova nada nesse app.
